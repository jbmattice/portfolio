About Me

I help teams make their digital experiences usable for everyone, not just compliant on paper. I've spent years doing that inside Fairfax County Public Schools, one of the largest school districts in the country. I'm used to working in complex environments with real constraints — legacy systems, non-technical stakeholders, huge scale. My background is in education and psychology, which shapes how I approach accessibility. I don't just flag WCAG violations. I translate what needs to change into language developers and content teams can actually act on. That's the part I'm really good at — bridging the gap between the standard and the human.

Cognitive and Human-Centered Design
  • Reducing Cognitive Load and mental fatigue by:
    • Minimizing visual noise.
    • Avoiding timed interactions.
    • Structuring complex workflows.
  • Support varying attention spans and reading levels by:
    • Using plain language.
    • Organizing content with headings.
    • Breaking up blocks of text into shorter sentences and bulleted lists.
    • Using accessible hyperlinks with clear calls to action.
  • Usability Beyond Technical Compliance:
    • Focusing on how real people experience an interface.
    • Moving past checkbox audits.
    • Including neurodivergent individuals, assistive technology users, and older/younger people.
Semantic Code and Visual Craft
  • Extending Native HTML with CSS:
    • Building rich and engaging interfaces.
    • Digging deep into CSS to build custom, missing UI components out of native, accessible markup.
    • Minimizing JavaScript overhead.
  • Respecting User Preferences: Building resilient components that automatically adapt to light/dark themes, high-contrast modes, and reduced-motion preferences.
  • Fluid and Inclusive Layouts:
    • Using device-level settings.
    • Using modern CSS (like fluid typography, Flexbox, and Grid).
    • Making sure layouts scale across all devices.
Auditing, Remediation and Trusted Tester Compliance
  • Evaluating digital products using the DHS Trusted Tester Methodology.
  • Applying standardized, repeatable testing protocols.
  • Combining automated and manual testing.
  • Translating issues into clear, developer-friendly fixes that preserve both accessibility and UI integrity.

Legacy Course Catalog and Transportation Application

Accessibility rebuild • Mobile-first • Section 508 / WCAG 2.1 AA

Modernized and optimized legacy content into a mobile-responsive, 508-compliant platform. The work focused on making course and transportation information usable for students and parents across devices and assistive technologies.

Key Insight: Accessibility issues often stem from structural constraints inside the system, not just visual design choices.

Academy Transportation Finder (opens in new tab)
Challenges
  • Legacy content was not designed for accessibility and required substantial restructuring
  • A mandatory CMS shell introduced layout and styling constraints that limited direct fixes
  • Known accessibility defects existed in the underlying structure and brand styling
  • The experience needed to work reliably on mobile, desktop, and with assistive technologies
Solutions
  • Re-architected the content using semantic HTML to improve structure and assistive technology support
  • Engineered custom HTML5/CSS3 workarounds to compensate for shell-level accessibility defects
  • Remediated layout, navigation, contrast, focus, zoom, and reflow issues
  • Added print support with a dedicated print stylesheet for users who needed hard copies
  • Made incremental improvements over a three-month period while working within existing constraints
Tradeoffs and Decisions

I could not change the CMS shell or brand styling directly, so I prioritized accessibility first and then improved usability with targeted enhancements such as print functionality and CSS refinements. If I had access to the shell CSS, I would have resolved more issues at the source; instead, I focused on the highest-impact changes that could be delivered safely within the existing system.

Impact: Students and parents now have full access to the information using screen readers, keyboard navigation, and zoom up to 400%. The experience is also more usable on mobile and desktop, with clearer structure, better performance, and improved print output.

Accessible Gantt Chart for Curriculum Timeline

Data visualization • System design • WCAG compliance

Designed and implemented a reusable, accessible timeline system across 100+ curriculum pages by grade level and subject area to visualize learning progression by quarter and week.

Key Insight: Accessibility and translation needs shaped the information design as much as the visual presentation.

Grade 5 Math Curriculum (opens in new tab)

Challenges
  • Organizational leadership needed a visual representation of the school year by week and quarter.
  • The source content was provided in a table, but a traditional table would not work because the data required merged and split cells.
  • Image-based solutions would not translate cleanly for families who needed multilingual access.
  • Many attempted solutions did not mesh with the CMS, requiring multiple iterations to find a workable CSS-only approach.
  • Unit lengths varied significantly, from 3-week units to 5-week units, and the design needed to adapt across grade levels and subject areas.
  • The solution had to be manually replicated across 100+ pages, so it needed to be scalable and efficient to maintain.
Solutions
  • Rejected image-based approaches so the content would remain accessible and translatable.
  • Avoided traditional tables because split and merged cells would create structural and accessibility problems.
  • Researched and tested CSS-only chart patterns until I found a solution that worked within the CMS.
  • Designed a flexible structure that could support varying unit lengths and differences across subjects and grade levels.
  • Created custom CSS that transformed the timeline into a mobile-friendly bulleted list on smaller screens.
  • Ensured the final pattern remained usable with keyboard navigation and screen readers.
Tradeoffs and Decisions

I needed a solution that balanced accessibility, translation, and maintainability while working within CMS constraints. I chose a CSS-only pattern because it could scale across 100+ pages, support mobile users, and adapt to changing content structures without introducing unnecessary complexity.

Impact: Teachers now share these pages with parents at the beginning of the school year during back-to-school night. Instead of relying on high-level PDFs or handouts, parents can see the exact standards taught in each unit by week and by quarter. This gives families a clearer understanding of the curriculum and improves communication between home and school.

Accessibility Audit and Remediation Guidance

WCAG audit • Developer collaboration • Remediation guidance

Conducted a comprehensive WCAG 2.2 AA audit of a dynamic web platform, evaluating 55 success criteria and identifying critical accessibility issues.

Key Insight: Many accessibility barriers came from structure, labeling, and responsive behavior, not just color contrast or obvious missing text.

Challenges
  • Missing or inconsistent alt text for images and functional graphics
  • Reflow and zoom issues causing horizontal scrolling at higher magnification
  • Unclear link purpose and inconsistent labeling across controls
  • ARIA and semantic HTML mismatches affecting screen reader output
Approach
  • Used DHS Trusted Tester methodology to evaluate compliance systematically
  • Tested with NVDA, keyboard navigation, ANDI, and IBM Accessibility Checker
  • Reviewed structure, labels, reading order, and responsive behavior
  • Documented findings and recommendations for the development team
Sample Findings
  • Missing alt text: Images were hidden or lacked meaningful descriptions.
  • Reflow issues: Content required horizontal scrolling at higher zoom levels.
  • Unclear link purpose: Links and controls were inconsistently labeled.

Outcome: Provided detailed remediation guidance and collaborated with developers to improve accessibility and awareness across the platform.

High-Volume K-6 Educational PDF Workbooks

PDF Remediation • Public Sector • WCAG 2.2 AA and PDF/UA

Led the accessibility architecture and remediation strategy for a massive suite of public summer curriculum workbooks spanning grades K-6. The benchmark project focused on a highly visual, 54-page 2nd Grade Language Arts workbook containing irregular multi-column layouts, tables, and vendor-provided assets.

Grade 2 Language Arts Packet (PDF opens in new tab)

The Process

Established a multi-stage production pipeline: content teams initiated layouts in Google Docs, utilized Grackle Docs for initial structural analysis, and exported to PDF. I then performed deep-level manual remediation in Adobe Acrobat Pro—rigorously walking the Tag Tree and verifying the Reading Order panel—before validating compliance using the PAC (PDF Accessibility Checker) engine.

Challenges
  • Non-Interactive AT Navigation: The document is designed to be printed rather than filled out digitally, yet it still had to remain fully navigable and coherent for students utilizing Assistive Technology (AT) without form fields. Very little documentation exists for this specific engineering requirement.
  • Inaccessible Third-Party Vendor Assets: Embedded handwriting tracing pages featured a black line example followed by low-contrast grey lines for tracing. The vendor-supplied grey lines failed contrast requirements, creating a systemic barrier that could not be modified at the source.
  • Velocity and Scale: Manually remediating tag structures, establishing reading flows, and fixing reading orders across 50 to 60+ pages per packet presents an immense time and resource bottleneck.
Solutions and Technical Tradeoffs
  • Custom Static Tagging Structures: Engineered a predictable, linear keyboard reading order without relying on interactive form controls. Visual placeholders and text indicators were meticulously mapped to structural paragraph tags (<P>) and list elements to guide AT users through tasks meant for print.
  • Vendor Risk Management: Documented the vendor-driven contrast failures as an institutional compliance exception. Compensated by rewriting explicit descriptive alt-text and layout instructions to ensure the *intent* of the handwriting exercises was communicated clearly via screen readers.
  • Pipeline Automation: Created a reusable tagging template playbook for the curriculum staff, shifting accessibility upstream into Google Docs to radically reduce manual clean-up time in Acrobat.

Impact: Established a scalable roadmap for the remaining K-6 packets, ensuring thousands of families have baseline summer learning access. The 2nd-grade benchmark artifact successfully passes automated PAC verification while preserving print fidelity.

Accessible Portfolio System & Architecture

Design system • Zero-dependency HTML/CSS • WCAG 2.2 AA

Architected and engineered a lightweight, high-performance personal portfolio from scratch using semantic HTML5, modern CSS custom properties, and standard-compliant WAI-ARIA patterns.

Key Insight: True accessibility starts with low-complexity foundations—avoiding heavy frameworks allowed 100% automated audit passes and flawless screen reader behavior.

Technical Highlights
  • Robust Keyboard Navigation: Custom tablist implementation strictly following WAI-ARIA Authoring Practices (APG) with automatic arrow-key focus management.
  • Fluid & Accessible Typography: Uses Atkinson Hyperlegible scaled via clamp() functions to support 400% zoom without horizontal scrolling or reflow breakage.
  • High Contrast Mode Hardening: Tailored forced-colors: active media queries to guarantee native visual boundaries and focus indicators in Windows High Contrast Mode.
  • Fluid Viewport & Reflow Architecture: Engineered using CSS clamp() fluid typography and Every Layout primitives (.l-sidebar and .l-cluster) to satisfy WCAG 1.4.10 Reflow down to 320px viewports without horizontal scrolling or reflow breakage up to 400% zoom.
  • Touch Target & Viewport Bounds: Enforced a minimum 44×44px touch target area (WCAG 2.5.8) across all interactive controls, custom tab triggers, and detail summaries for mobile and tablet viewports.
  • Token-Based Color System: Native light-dark() color engine using custom properties passing WCAG 2.2 AA contrast ratios across light and dark display modes.

Impact: Achieves a 100% Lighthouse Accessibility score with zero issues identified via axe DevTools (4.12.1) and AInspector scans, alongside full manual verification using NVDA, voice control, and touch target standards across all viewport sizes.
